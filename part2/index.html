TL;DR — what changed in phase one?

Part 2 of the article series covers Phase 1 of the migration: replacing Recoil with Jotai everywhere. The goal was intentionally narrow: remove Recoil, keep behavior unchanged, and postpone deeper architecture work.

  • Phase one was intentionally boring. Recoil disappeared, Jotai became the atom layer, and application behavior stayed the same
  • Simple atoms moved almost 1:1. Most changes were import paths, hook names and atom references
  • Reset semantics mattered. We used atomWithReset because it mapped better to the existing cleanup behavior than plain atom
  • The promotion selector became a composite atom. Jotai’s atom(get, set) let us keep the same component-facing surface
  • Some debt intentionally stayed. couponJobsCheck and rerenderFilters were moved 1:1 and left for later architecture work
  • Tests changed, but not magically. The shared setup moved from RecoilRoot.initializeState to a similar but slightly more explicit createStore() setup
The short answer: phase one removed Recoil safely, introduced Jotai everywhere, and prepared the ground for the actual architecture work

What phase one was supposed to do

In Part 1 we described why Recoil had to go, why Jotai was the first candidate, and why Redux Toolkit should wait until we tackle explicit application flows. Phase one had one narrow goal: remove the deprecated dependency safely, without redesigning the application.

Definition of Done — achieved:
  • zero imports from recoil anywhere in the codebase
  • all unit tests green
  • no intentional behavior changes
  • no application-flow redesign — that comes later

The migration touched every file that previously imported from recoil. In practice, that meant more than 115 source files, 12 atom files, one selector, the test infrastructure and the application entry point. The business logic was intentionally kept unchanged.

The goal was not to make the architecture perfect. The goal was to remove Recoil without changing how the application behaves

The inventory, but not as a file dump

Before writing Jotai code, we still had to map the current Recoil surface area. Internally, that meant a full inventory: every atom, every selector, every import, and every test wrapper. For an article, however, the file-by-file list is less interesting than the kinds of cases we found.

The migration was not one problem repeated twelve times. It was several different shapes of state that happened to share the same Recoil dependency.

CaseExamplesWhy it mattered
Small UI atomsnavigation, rightSidebarEasy 1:1 migration. These were the calm, mechanical cases.
Session/meta-stateuser, selectedRole, allowedSubsidiaries, currencyStill migrated to Jotai in phase one, but worth reviewing later because they influence permissions, queries and visible data.

So yes, we had the full inventory. But the useful story is not “here are all files”. The useful story is: which migration pattern did each state shape require?

The mechanical migration

The snippets below are examples, not a full list of every changed file. Most atoms followed the same mechanical pattern: Recoil's key disappeared, the default value became the Jotai initial value, and the atom moved to src/jotai/.

I kept couponJobs in the examples on purpose. It is one of the atoms we will revisit in the next part when we move the polling flow to Redux Toolkit. In phase one, however, it was intentionally migrated 1:1.

Why atomWithReset, not atom

Part 1 showed the basic migration with plain atom from jotai. In practice, the migrated atoms use atomWithReset from jotai/utils. This was deliberate.

The reason is reset semantics. In a promotion-heavy application, navigating away from a promotion must clean up a lot of state: loaded promotion data, loading flags, edit mode, copy flag, revision list and coupon state. With a plain atom, the call site needs to know the initial value.

plain atom — reset requires knowing the default 
// with plain atom — requires knowing the initial value at the call site
const setPromotion = useSetAtom(promotionAtom);
setPromotion(undefined); // you need to know this is the default

With atomWithReset, the initial value stays sealed inside the atom definition. The call site only sends RESET.

atomWithReset + RESET 
import { useSetAtom } from 'jotai';
import { RESET } from 'jotai/utils';
import { promotionAtom } from '#jotai/promotion-state-atom';

const resetPromotion = useSetAtom(promotionAtom);

// On navigation away — reset to the initial value defined in the atom
resetPromotion(RESET);

This becomes even more useful with the composite promotion state, because resetting the composite atom can reset all individual atoms at once.

resetting the composite promotion atom 
const setPromotionState = useSetAtom(promotionStateAtom);

// Resets all 8 individual atoms to their defaults simultaneously
setPromotionState(RESET);
Lesson learned: for a migration from Recoil, atomWithReset often maps better to existing reset behavior than a plain Jotai atom

The composite atom pattern

The most interesting case was promotion state. In Recoil, it was not just one large atom. It was a set of individual atoms plus a selector that combined them into a single readable and writable surface.

Before — selector/promotion-recoil-state.ts (simplified) 
import { atom, DefaultValue, selector } from 'recoil';

// Individual atoms
export const promotionState = atom<Promotion | undefined>({ key: 'promotion', default: undefined });
export const isLoadingState = atom<boolean>({ key: 'isLoading', default: true });
export const isSavingState = atom<boolean>({ key: 'isSaving', default: true });
export const modeState = atom<Mode>({ key: 'mode', default: Mode.Create });
// ... 4 more

// Composite selector providing a single read/write surface
export const promotionRecoilState = selector<PromotionRecoilStateType>({
    key: 'promotionRecoilState',
    get: ({ get }) => ({
        promotion: get(promotionState),
        isLoading: get(isLoadingState),
        isSaving: get(isSavingState),
        mode: get(modeState),
        // ...
    }),
    set: ({ set }, value) => {
        if (value instanceof DefaultValue) {
            set(promotionState, value);
            set(isLoadingState, value);
            // ...
            return;
        }
        set(promotionState, value.promotion);
        set(isLoadingState, value.isLoading);
        // ...
    },
});

The Jotai version kept the same idea structurally: individual resettable atoms plus a composite atom(get, set). The read side builds the object from individual atoms. The write side either resets everything, applies a function update, or writes a full object back into the individual atoms.

After — jotai/promotion-state-atom.ts (simplified) 
import { atom } from 'jotai';
import { atomWithReset, RESET } from 'jotai/utils';

// Individual atoms — each resettable independently
export const promotionAtom = atomWithReset<Promotion | undefined>(undefined);
export const isLoadingAtom = atomWithReset<boolean>(true);
export const isSavingAtom = atomWithReset<boolean>(true);
export const modeAtom = atomWithReset<Mode>(Mode.Create);
// ... 4 more

type PromotionStateUpdate =
    | PromotionStateType
    | typeof RESET
    | ((prev: PromotionStateType) => PromotionStateType);

// Composite atom — same component-facing surface as the old selector
export const promotionStateAtom = atom(
    (get): PromotionStateType => ({
        promotion: get(promotionAtom),
        isLoading: get(isLoadingAtom),
        isSaving: get(isSavingAtom),
        mode: get(modeAtom),
        // ...
    }),
    (get, set, value: PromotionStateUpdate): void => {
        if (value === RESET) {
            set(promotionAtom, RESET);
            set(isLoadingAtom, RESET);
            // ...
            return;
        }

        const prev = get(promotionStateAtom);
        const next = typeof value === 'function' ? value(prev) : value;

        set(promotionAtom, next.promotion);
        set(isLoadingAtom, next.isLoading);
        // ...
    }
);

The important part is not that the backend contract or GraphQL API changed — they did not need to. This was a frontend state surface migration: components could still work with one promotion state object, while the implementation underneath moved from a Recoil selector to a Jotai composite atom.

Partial update through the composite atom 
const setPromotionState = useSetAtom(promotionStateAtom);

// Partial update — only change isSaving, keep everything else
setPromotionState(prev => ({ ...prev, isSaving: false }));
Jotai did not force us to flatten the promotion state into one giant atom. We could keep the old “small atoms + composite interface” pattern

Provider and entry point

The application entry point was one of the smallest production changes. The relevant state-management change was simply replacing RecoilRoot with Jotai’s Provider.

Before — main.tsx (simplified)

import { RecoilRoot } from 'recoil';

ReactDOM.createRoot(
  document.getElementById('root') as HTMLElement

After — main.tsx (simplified)
import ReactDOM from 'react-dom/client';
import { Provider as JotaiProvider } from 'jotai';

ReactDOM.createRoot(
  document.getElementById('root') as HTMLElement

This is also why the migration was a good fit for phase one. The provider boundary was already clean. We did not need to thread new props through the application.

Testing setup changed, but not as dramatically as production code

The production changes were mostly mechanical. The testing setup changed too, but it would be misleading to say that tests became automatically simpler. The shared wrapper stayed structurally similar: we still have a test provider, a helper called getInitializeState, mock state objects, and atom values initialized before rendering.

The real difference is where and how that initialization happens. With Recoil, state was initialized inside RecoilRoot.initializeState through a snapshot callback. With Jotai, we create a store directly with createStore(), write values into it with store.set(...), and then pass that store to JotaiProvider.

Honest takeaway: the Jotai setup is not dramatically shorter. It is slightly more explicit, because the test store is created and prepared as a normal object before rendering

Same shape, different initialization point

Recoil:
RecoilRoot
  initializeState(snapshot => getInitializeState({ set: snapshot.set }))

Jotai:
const store = createStore()
getInitializeState({ store })
JotaiProvider store={store}

How Jotai initializes state in tests

With Jotai, the wrapper creates a dedicated store with createStore(), initializes it directly, and passes it into JotaiProvider. The helper still looks familiar, but instead of receiving Recoil’s snapshot setter, it receives a Jotai store.

After — mock-wrapper.tsx 
import { Provider as JotaiProvider, createStore } from 'jotai';
import { CouponStateMock, getInitializeState, PromotionStateMock }
  from './mock-jotai';

export const MockWrapper = ({
    children,
    role = Role.ProductRoot,
    rightSidebarState,
    promotionState,
    couponState,

    const store = createStore();

    getInitializeState({
        store,
        role,
        rightSidebarState,
        promotionState,
        couponState,

    return (
        <JotaiProvider store={store}>
            <MockedProvider mocks={mocks || defaultMocks(role)} addTypename={false}>
                <MemoryRouter>
                    <ProfileProvider>{children}</ProfileProvider>
                </MemoryRouter>
            </MockedProvider>
        </JotaiProvider>
    );
};

Mocking atom setters in individual tests

At first glance, the Jotai version can look more complicated than the Recoil version: Recoil used vi.spyOn, while Jotai uses vi.hoisted and vi.mock. That does not mean the application behavior became more complex. It is a test mechanics difference. With Jotai hooks imported from an ES module, the module boundary has to be mocked before the component imports it.

So this is not the example where Jotai made tests simpler. The assertion stayed the same: clicking the revisions button should call the atom setter with the expected right-sidebar state. The testing improvement came from the shared wrapper setup with createStore(), not from every individual mock.

Before — revisions-button.test.tsx
import * as recoil from 'recoil';

it('should call setRightSidebarState on click', async () => {
    const mockSetSidebar = vi.fn();

    // Spy on Recoil's hook
    vi.spyOn(recoil, 'useSetRecoilState')
        .mockReturnValue(mockSetSidebar);

    render(<MockWrapper><RevisionsButton /></MockWrapper>);

    const button = await waitFor(() =>
        screen.getByTestId(testId.promotionRevisionsButton)
    );
    fireEvent.click(button);

    expect(mockSetSidebar).toHaveBeenCalledWith({
        shouldRender: true,
        isRightSidebarCollapsed: false,
        showComments: false,
        showRevisions: true,
    });
});
After — revisions-button.test.tsx
const { useSetAtomMock } = vi.hoisted(() => ({
    useSetAtomMock: vi.fn(),
}));

vi.mock('jotai', async () => {
    const actual =
        await vi.importActual<typeof import('jotai')>('jotai');
    useSetAtomMock.mockImplementation(actual.useSetAtom);
    return { ...actual, useSetAtom: useSetAtomMock };
});

it('should call setRightSidebarState on click', async () => {
    const mockSetSidebar = vi.fn();
    useSetAtomMock.mockReturnValue(mockSetSidebar);

    render(<MockWrapper><RevisionsButton /></MockWrapper>);

    const button = await waitFor(() =>
        screen.getByTestId(testId.promotionRevisionsButton)
    );
    fireEvent.click(button);

    expect(mockSetSidebar).toHaveBeenCalledWith({
        shouldRender: true,
        isRightSidebarCollapsed: false,
        showComments: false,
        showRevisions: true,
    });
});

This is not a conceptual change. It is a library-level change. The test still verifies the same behavior: clicking the revisions button opens the right sidebar with revisions visible and comments hidden.

What we intentionally kept as-is

Part 1 identified two command-in-state atoms: boolean values that do not describe the world, but act as signals to trigger side effects.

  • couponJobsCheckAtom still triggers job fetching/polling
  • filterAtom.rerenderFilters still triggers filter UI synchronization after Excel import

Neither was fixed in phase one. Both were migrated 1:1 and marked as next-step candidates.

This is intentional technical debt. Fixing it means redesigning application flow, not replacing a state library

Fixing couponJobsCheckAtom means replacing the polling mechanism with explicit async actions. That is exactly what phase two is for. Mixing that into the Recoil → Jotai PR would have made the migration harder to review and riskier to test.

Verdict

The plan held. The simple atom migration was as mechanical as expected. The composite promotion state mapped naturally from Recoil’s selector to Jotai’s atom(get, set). The biggest production-side improvement was atomWithReset and the composite read/write atom. The test setup also became a little more explicit, but it stayed structurally similar to the Recoil setup.

Exactly as planned

  • 12 atoms migrated 1:1
  • hook renaming with no logic changes
  • command-in-state kept as-is
  • all tests green after migration

Better than expected

  • atomWithReset + RESET is cleaner than manual default resets
  • createStore() makes test state setup explicit, even if the wrapper stayed similar
  • composite atoms map well from Recoil selectors
  • no surprising component-level breakage

In numbers: more than 115 source files touched, 12 atoms and one selector moved, test infrastructure rebuilt, and recoil removed from the dependency tree. Zero intentional behavior changes.

Phase one did exactly what it was supposed to do: remove Recoil safely and prepare the ground for the actual architecture work

What comes next

Recoil is gone. The foundation is Jotai. The next chapter is the one that was always more interesting architecturally: moving coupon jobs polling to Redux Toolkit.

The current polling system after phase one is functionally unchanged:

still true after phase one 
// Still: a boolean trigger
couponJobsCheckAtom: boolean

// Still: job data in an atom
couponJobsAtom: CouponJob[] | undefined

// Still: logic spread across a hook with useEffect + useInterval
use-jobs-checker.ts: trigger → fetch → update → poll → notify

Phase two should not touch the simple Jotai atoms. Navigation, sidebar, user, subsidiary and currency stay where they are. Redux Toolkit enters only for the coupon jobs polling process, because that is a sequence of named events with observable lifecycle, not just “a value that might change”.

target direction for phase two 
couponJobs/triggerCheck          → intent to check
couponJobs/startPolling          → polling started (from async thunk)
couponJobs/jobsUpdated           → data received
couponJobs/pollingFinished       → all jobs done
couponJobs/pollingFailed         → error
Boundary after phase two: if the state requires understanding a lifecycle, use Redux Toolkit. If it is a small shared value, keep it in Jotai

Series

Part 1 explained the decision. Part 2 removed Recoil and introduced Jotai everywhere without changing behavior. Part 3 should be the real architecture test: moving coupon jobs polling from a boolean trigger to an explicit Redux Toolkit flow
