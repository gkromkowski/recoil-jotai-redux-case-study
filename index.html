TL;DR — should you read the whole thing?

A short version of the decision: Recoil had to be replaced, but the real question was not only which library to pick. It was who should own each kind of state.

  • Start boring. Phase one should be a safe 1:1 Recoil → Jotai migration, with no intentional behavior changes
  • Jotai stays. It is a good fit for lightweight atom state: navigation, sidebars, small shared UI flags, and simple Recoil replacements
  • Redux Toolkit is for process state. It makes more sense for coupon jobs, polling, async lifecycle, session/meta-state, and flows that need better debugging
  • Apollo and React Hook Form still have ownership. Apollo handles backend-data loading with careful cache policy, while RHF owns edited form values
  • The final decision is hybrid, but explicit. Jotai and Redux Toolkit can coexist if their ownership boundaries stay clear
The short answer: migrate Recoil to Jotai first, then introduce Redux Toolkit only where the application flow actually needs it

Starting point

In our project, we had been using Recoil for global or shared state for quite some time. It was not a single giant store holding the whole application, but Recoil appeared in several important areas: user session, roles, selected subsidiary, UI flags, promotion state, filters, coupon detail, and the flow related to generating coupons and polling background jobs.

For a long time, it worked well enough. We had atoms, selectors, a few hooks, and components that could communicate through shared state.

The problem did not start with a concrete bug in our application. It started with the risk of keeping an important part of the application on top of a library that no longer looked like a safe long-term choice. The official Recoil repository was archived and became read-only, the latest release was 0.7.7 from 2023, and there were practical concerns in the issue tracker around compatibility with newer React versions, for example React 19.

That did not mean our application suddenly stopped working. It meant that the next React upgrade or a larger ecosystem change could become our problem to solve.

This was not only a team preference: the public Recoil repository is archived/read-only, the latest release is 0.7.7 from 2023, and there is an open issue about React 19 support

The first intuition was simple: if Recoil needs to be replaced, the most natural candidate seems to be Jotai. And that really makes sense.

The first idea was straightforward: Recoil → Jotai. Small diff, lower risk, similar work with small state atoms

But then a second question appeared. If we are already touching state management, changing hooks, atoms, test wrappers and providers, should we use that moment to check whether the problem is only Recoil as a dependency, or also the way some application flows were built? It was also a good opportunity to see whether selected areas would benefit from a different tool — one that makes process flow more visible, easier to debug, and easier to test.

This is not just “Jotai or Redux?”

The more we looked at the current code, the less useful the question “which library is better?” became. The better question was: what types of state do we have in the application, and which tool fits each type best?

Not all state is the same

  • backend data
  • edited form data
  • global UI state
  • session and view meta-state
  • async processes
  • state used as a command

The real shift

If we call everything “global state”, we quickly start discussing libraries instead of ownership.

And ownership turned out to be the most important part of this migration.

This is where we need to be careful. A promotion is backend data, an edited form, a screen lifecycle with create/edit/restore, a separate copy flag, and a save/validation process

We also should not mix the semantics of mode with copy flow. In the current code, mode describes the main way the screen and form are initialized: creating a new promotion, editing an existing one, or restoring. “Copy” is not the same kind of form lifecycle mode. It is additional information: the form may start from an existing promotion, but it eventually behaves like creating a new one.

promotion-detail.tsx
const isCreateOrRestoreMode = [
  Mode.Create,
  Mode.Restore,
].includes(modeRecoilState);

// copy-flow is a separate flag, not a separate Mode value
const isCopiedPromotion = ...;

For the migration, this means we should move mode values according to their current semantics, and treat copy flow as separate state or metadata. Otherwise, we may accidentally introduce a simplification in the new state layer that the old code did not actually have.

In the current implementation, promotion detail effectively works on three layers at the same time: Apollo loads the data, Recoil stores meta-state and a mirror of the full promotion, and React Hook Form stores the edited form values. This works, but it increases the risk of state ownership drifting apart.

Apollo, Recoil and React Hook Form: three layers to clean up

Apollo is already a server-state layer

We use Apollo Client in the project. It is easy to think about Apollo only as a layer for executing GraphQL queries and mutations, but Apollo is also a cache. That means Apollo is already a kind of server-state layer.

In the current code, however, the situation is more complicated than the target ownership model. Promotion data comes from Apollo, is then mirrored into Recoil by usePromotion, and is then used as defaultValues for React Hook Form. So currently, not two but three layers participate in this flow.

Apollo cache       → promotion
Recoil             → promotion mirror + meta-state
React Hook Form   → promotion form values
Three sources of truth are usually not architecture. They are a future bug request. Apollo should remain the main backend-data loading layer, but that does not mean blindly trusting the cache
Important repository context: we cannot simply say “Apollo cache is the source of truth”. In many places, we intentionally force fresh data with network-only, because the data depends on the current user context: country, subsidiary, role, promotion revision, or job status
use-promotion.ts
useQuery(..., {

    revision: revisionNumber || 0,
  },
  fetchPolicy: fetchPolicy || 'network-only',
});
promotion-detail.tsx
await getValidation({

});
use-comments.ts

This is not an argument against Apollo. It is a reminder that, in this application, server state is strongly tied to context: country, subsidiary, role and the current view. If the cache is not aligned with that context, the UI can show stale data.

Why Jotai was the first candidate

Jotai was the natural first candidate because it is close to Recoil in how we work with small pieces of state. If today we have a simple atom, the migration can be quite calm.

Problem: command-in-state

One of the most interesting findings was a pattern I would call command-in-state: a state value that does not describe the world, but acts as a command to trigger an effect.

coupon-jobs-recoil-state.ts
export const couponJobsCheckRecoilState = atom<boolean>({
  key: 'couponJobCheck',
  default: true,
});

At first glance, this looks innocent. We have a boolean that says whether coupon jobs should be checked. But in practice, this boolean is a trigger.

coupon-manager.tsx
useEffect(() => {
  setCouponJobsCheckRecoilStateValue(true);
}, [setCouponJobsCheckRecoilStateValue]);
coupon-manager.tsx
onGenerate({
  quantity,
  redemptionLimit: activeTab,
  pattern: couponCodePattern,
  async: true,
  onThen: () =>
    quantity > 1 && setCouponJobsCheckRecoilStateValue(true),
});

The coupon generation mutation itself lives in use-coupons.ts:

use-coupons.ts
const generateCoupons = ({
  quantity,
  redemptionLimit,
  pattern,
  partyIds,
  async,
  onThen,
}: GenerateCouponsProps) => {
  generate({
    // ...
  }).then(() => {
    const isAsync = !!(quantity > 1 && async);

    emitSuccess({
      action: CouponAction.Generate,
      async: isAsync,
    });

    if (!isAsync) {
      refetch();
    }

    if (onThen) {
      onThen();
    }
  });
};

3

This works. The problem is not that the code must be “bad”. The problem appears when we need to trace who started polling, whether polling is already running, and what happens after two fast clicks

What the current polling looks like

The current polling lives in use-jobs-checker.ts. Simplified:

use-jobs-checker.ts
useInterval(
  () => handleGetJobs(username),
  couponJobsRecoilStateValue?.length ? interval : null
);

useEffect(() => {
  if (couponJobsCheckRecoilStateValue && username && !error) {
    setCouponJobsCheckRecoilStateValue(false);
    handleGetJobs(username);
  }
}, [
  couponJobsCheckRecoilStateValue,
  error,
  handleGetJobs,
  setCouponJobsCheckRecoilStateValue,
  username,
]);

Important detail: the trigger does not mean polling “always runs” after the flag is set. The flow has two steps. couponJobsCheck starts the first fetch through handleGetJobs, and useInterval runs only when there are jobs to observe: couponJobsRecoilStateValue?.length ? interval : null.

More precisely: the trigger means “kick off the first check”, while the interval is only conditional continuation of polling when running jobs exist

This hook does several things at once:

runs QUERY_JOBS through useLazyQuery
reacts to couponJobsCheckRecoilState
resets the trigger from true to false
runs one immediate check
starts polling through useInterval
detects finished jobs
shows notifications
updates global jobs state

This is why Redux Toolkit entered the discussion. Not because Redux is better for every kind of state, but because here we are dealing with a process.

We have process start, process status, polling, completion conditions, errors, notifications, possible duplication and a need to debug the sequence of events

Minimal Recoil → Jotai migration

As we can see, use-jobs-checker already has quite a lot of responsibility. Still, the first migration step does not need to solve the entire polling problem immediately. If the goal of phase one is to safely and quickly remove Recoil, we can first move atoms 1:1 to Jotai and preserve current behavior.

A minimal migration could look like this:

- import { atom } from 'recoil';
+ import { atom } from 'jotai';

- export const couponJobsCheckRecoilState = atom<boolean>({
-   key: 'couponJobCheck',
-   default: true,
- });
+ export const couponJobsCheckAtom = atom<boolean>(true);
- const setCouponJobsCheckRecoilStateValue =
-   useSetRecoilState(couponJobsCheckRecoilState);
+ const setCouponJobsCheck = useSetAtom(couponJobsCheckAtom);

- onThen: () => quantity > 1 && setCouponJobsCheckRecoilStateValue(true),
+ onThen: () => quantity > 1 && setCouponJobsCheck(true),
This is a good first step if the goal is a safe Recoil migration. But architecturally, the problem remains. We still have a boolean trigger, polling started by an effect, and scattered flow

What this could look like in Redux Toolkit

In Redux Toolkit, this process can be described more explicitly. Instead of hidden flow based on a boolean trigger and useEffect, we can have a sequence of actions:

A minimal slice candidate could look like this:

coupon-jobs-slice.ts
import { createSlice, PayloadAction } from '@reduxjs/toolkit';
import { CouponJob } from '#types/generated-types';

interface CouponJobsState {
  jobs: CouponJob[] | null;
  shouldCheck: boolean;
  lastCheckedAt: number | null;
}

const initialState: CouponJobsState = {
  jobs: null,
  shouldCheck: true,
  lastCheckedAt: null,
};

const couponJobsSlice = createSlice({
  name: 'couponJobs',
  initialState,
  reducers: {
    triggerJobsCheck: state => {
      state.shouldCheck = true;
    },
    startJobsCheck: state => {
      state.shouldCheck = false;
      state.lastCheckedAt = Date.now();
    },
    setJobs: (state, action: PayloadAction<CouponJob[] | null>) => {
      state.jobs = action.payload;
    },
    clearJobs: state => {
      state.jobs = null;
    },
  },
});

export const {
  triggerJobsCheck,
  startJobsCheck,
  setJobs,
  clearJobs,
} = couponJobsSlice.actions;

export default couponJobsSlice.reducer;

This still is not the final perfect model. shouldCheck can still smell like a trigger, so the next step could be a full async flow through a thunk or middleware.

But even this simple slice has one advantage over a boolean atom: every step is named as an action.

Profile / subsidiary context: overlapping ownership

Profile, roles and subsidiaries are less spectacular than polling, but architecturally they are also important. In the current code, responsibility for user/subsidiary context is split between ProfileProvider and LayoutComponent.

This is not necessarily a bug. These things often grow naturally: a provider loads profile data, the layout needs it to render the application, and then roles, selected subsidiary, localStorage and dependent queries join the party. The problem starts when multiple places can update similar context and it becomes hard to answer which one is the source of truth.

In the current code, ProfileProvider handles session bootstrap: it loads getUserData, sets userRecoilState, allowedSubsidiariesRecoilState, currencyRecoilState, availableRolesState, and after selected subsidiary changes it also fetches customer segments. LayoutComponent reacts to subsidiary in the URL during navigation, validates whether that subsidiary is allowed, fetches user data again, and also updates user/subsidiary/currency context.

}

Boundary example: rerenderFilters

I would keep filters in the article, but not as a random “bug found along the way”. This is more of a boundary example. rerenderFilters shows that not every problem found in Recoil automatically means “move this to Redux”.

The atom looks innocent:

filter-recoil-state.ts
type FilterRecoilStateType = {
  rerenderFilters: boolean;
};

export const filterRecoilState = atom<FilterRecoilStateType>({
  key: 'rerender-filters',
  default: { rerenderFilters: false },
});

But when we look deeper, the problem is probably not Recoil itself.

First we need to clarify ownership between RHF, the Filter() model, Excel import and filter UI. Only then can we decide whether this needs Redux, Jotai, or just a better local data flow.

The main conclusion: state ownership

After this analysis, the most important conclusion was not “Redux is better” or “Jotai is better”. The most important conclusion was: we need to separate responsibilities.

Apollo Client

Backend-data loading and server-state layer, with careful cache policy.

  • promotions
  • coupons
  • stores/subsidiaries
  • roles
  • jobs as backend data

React Hook Form

Edited form state.

  • edited promotion fields
  • validation
  • dirty/touched/errors
  • current form values

Jotai

Simple atom-based shared UI state.

  • collapsed navigation
  • right sidebar
  • small shared UI flags
  • simple replacement for part of Recoil atoms

Redux Toolkit

Application processes / flow / session meta-state.

  • coupon jobs polling flow
  • sessionStatus
  • currentPromotionId
  • mode create/edit/restore + separate copy flag
  • explicit application processes

Local state

Component-only UI.

  • local dropdown open/closed
  • hover
  • expanded row
  • temporary input state

URL

Shareable/search state.

  • search params
  • shareable filters
  • pagination visible in the address
  • selected tab, if it should survive refresh

Our hybrid compromise

In the end, we did not choose “Jotai instead of Redux” or “put everything into Redux”. A hybrid compromise made more sense:

Jotai = lightweight atom layer
Redux Toolkit = explicit process/flow layer

We do not assume the path “Recoil → Jotai → Redux for everything”. A more realistic split is: Jotai stays as a lightweight atom layer for simple shared/UI state, while Redux Toolkit is added only where state starts becoming a process.

Why not jotai-redux?

There is also an obvious question: if we plan to use both Jotai and Redux Toolkit, should we connect them with jotai-redux?

For this project, probably not. jotai-redux is useful when you want to expose a Redux store through a Jotai atom. Its atomWithStore creates an atom from a Redux store and supports two-way binding: the state can be changed from both the Redux side and the Jotai side.

That is exactly why we do not want to introduce it by default. The main point of this migration is not just to replace one state library with another. The main point is to make ownership clearer.

Jotai
- owns lightweight atom state
- navigation
- right sidebar
- small shared UI flags

Redux Toolkit
- owns explicit process state
- coupon jobs / polling
- async lifecycle
- selected session/meta-state, if needed

If we connect both layers automatically, we risk hiding the boundary again. Components could update Redux through Jotai atoms, or read Redux state as if it were local atom state. That may be useful as a temporary migration bridge, but it is not the architecture we want as the default.

Decision: we do not introduce jotai-redux at this stage. Jotai and Redux Toolkit should coexist, but with explicit ownership boundaries rather than automatic two-way synchronization

The first step is Recoil → Jotai. The goal is to safely remove the deprecated dependency. We do not try to fix the whole architecture in the same PR.

The second step, without the Recoil pressure, is selected processes in Redux Toolkit. Most likely, coupon jobs / polling comes first, because the benefit is concrete. Later we can look at session/meta-state, selectedRole, selectedSubsidiary, currentPromotionId, create/edit/restore modes, the copy flag, and other places where the application has explicit flow rather than just a simple value.

Summary

The first intuition was simple: Recoil is deprecated, so let’s move to Jotai.

Then came the second thought: if we are already touching state management, maybe we should also compare Redux Toolkit and use this situation to improve the application flow.

The final conclusion is more nuanced. Jotai solves the short-term problem: it allows us to safely replace Recoil because it is close to the current atom-based approach.

Redux Toolkit solves a different, longer-term problem: it helps organize processes, async flow, polling, session/meta-state, tests and debugging in places where plain atoms start to be insufficient.

Jotai = lightweight atom layer
Redux Toolkit = explicit process/flow layer

The most important conclusion is not “Redux Toolkit is better than Jotai”. It is also not “Jotai is enough and Redux is unnecessary”.

The most important conclusion is: first separate the types of state and their ownership. Only then does choosing a library start to make sense.

What next?

This article is the first part of the story, not the final verdict. The plan is to describe the next steps as they happen: how the migration went, what broke, which assumptions were right, and whether the hybrid approach was actually worth the extra complexity.
